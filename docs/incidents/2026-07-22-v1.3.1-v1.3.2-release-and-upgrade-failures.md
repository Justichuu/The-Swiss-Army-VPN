# v1.3.1 release and v1.3.2 upgrade failures

Date: 2026-07-22
Status: Resolved in v1.3.3

## Summary

Two separate release defects prevented the new installer work from reaching a usable installed state:

1. The `v1.3.1` tag pointed to a commit whose application metadata was still `1.3.0`. The tagged build correctly rejected that mismatch, so the intended v1.3.1 artifacts were not produced by that tag.
2. The immutable `v1.3.2` package built, published, and passed package checksum validation, but its live managed-upgrade path rejected a correctly staged 12-file installation because one validator still required exactly 10 files.

The v1.3.2 installer rolled the attempted upgrade back successfully. The existing VPN profile, connection state, saved sign-in, certificate, firewall rules, server choice, and v1.1.2 application files were preserved.

## User impact

- v1.3.1 could not be treated as the intended compiled release because its tag and source version disagreed.
- v1.3.2 was safe to download and inspect, but upgrading the existing managed v1.1.2 installation stopped with:

  > The staged upgrade failed its publisher, version, or file-layout check. The previous installation was restored.

- Three abandoned v1.3.1 draft releases accumulated while the broken release flow was retried. They were later removed without changing the published immutable v1.3.1 release.
- No VPN or firewall configuration was lost. The rollback path restored the previous installation.

## Timeline

1. Qwen-generated error-checking changes renamed PowerShell variables that collided with the automatic `$PROFILE` variable. The intent was correct, but three stale `$profile` references remained in the preserved-profile state sanitizer.
2. The `v1.3.1` tag was created before the repository's version metadata was consistently updated. GitHub Actions found the mismatch and failed the tagged build.
3. Later commits aligned the v1.3.1 source, package paths, native installer, Emergency Unlock executable, assets, and checksums, but they could not repair the already-created immutable tag.
4. v1.3.2 fixed the stale variable references, supported the relevant upgrade versions, repaired a malformed pinned `actions/download-artifact` commit SHA, and published four verified immutable assets.
5. The first real v1.1.2 to v1.3.2 upgrade constructed the intended 12-file staged installation, then rejected it because a hardcoded validator still expected 10 files.
6. Rollback restored the v1.1.2 installation and left the VPN-related system state unchanged.
7. v1.3.3 replaced the hardcoded count with a shared, version-aware exact-layout definition and added staged-upgrade construction to package validation.

## Root causes

### Incorrect v1.3.1 tag target

The tag named `v1.3.1` referenced source whose assembly, file, manifest, runtime, and build-script versions were still `1.3.0`. The release build intentionally treats disagreement between the tag version and source version as fatal.

### Drift between payload construction and validation

The managed-upgrade stage contained these 12 required files:

1. `Emergency Unlock.exe`
2. `Switzerland VPN.exe`
3. `Switzerland VPN.ico`
4. `Switzerland VPN.png`
5. `Switzerland VPN Background.png`
6. `Update Switzerland VPN.ps1`
7. `Uninstall Switzerland VPN.ps1`
8. `Emergency Unlock.ps1`
9. `Switch Switzerland VPN Server.ps1`
10. `VPN Server.txt`
11. `VPN Servers.txt`
12. `install-ownership.json`

The copy logic evolved as Emergency Unlock and the Swiss server pool were added, but a separate check remained `Count -ne 10`. A temporary attempt to satisfy that number by omitting `VPN Servers.txt` only hid the underlying drift. Restoring the required server-pool file made the stale count fail deterministically.

### Incomplete model-generated rename

Renaming `$profile` was necessary because PowerShell variable names are case-insensitive and `$PROFILE` is an automatic variable. However, the generated edit renamed the loop variable without updating all reads inside the object-copy block. This defect was fixed before v1.3.2, but it demonstrated that parser-clean model output was not sufficient validation.

## Contributing factors

- Project owner note: I trusted Qwen like a dipshit and treated confident-looking error checking as if it had been exercised end to end. It had not.
- The release process proved compilation, package checksums, PowerShell parsing, and top-level package structure, but did not construct and validate the exact managed-upgrade stage.
- The first authoritative end-to-end upgrade test happened only after v1.3.2 was published.
- Multiple related changes—new executables, server-pool support, directory renames, version bumps, and release automation—landed close together, making duplicated assumptions easier to miss.

## Corrective actions

v1.3.3 makes these changes:

- One function defines the exact managed-install files for a given version.
- Existing-install validation and staged-install validation use that same definition.
- One staging function constructs the upgrade payload used by both the real upgrade and package-validation test.
- Every release build now creates a staged managed installation and verifies its exact names, item types, reparse-point status, publisher, and file version.
- The build continues to reject disagreement among tag, assembly, manifest, runtime, installer, and build-script versions.
- Immutable release and asset verification remains mandatory after publication.

## Verification

Before publication, v1.3.3 passed:

- C# compilation with warnings treated as errors;
- PowerShell parser validation;
- package checksum validation;
- exact staged managed-upgrade layout validation;
- publisher and `1.3.3.0` file-version validation;
- validation after extracting the distribution ZIP;
- GitHub Actions validation on both the branch and pull request.

## Post-release verification

The exact published and GitHub-attested v1.3.3 distribution completed the real
v1.1.2 to v1.3.3 upgrade successfully on the machine that reproduced the
v1.3.2 failure.

The deployed-state audit confirmed:

- the application launched from `F:\Program Files\Switzerland VPN` and visibly
  reported `v1.3.3`;
- the widget reported `DISCONNECTED` and `Normal internet is available`, so the
  absence of active kill-switch rules was the expected unarmed state;
- application, ownership record, state record, and uninstall registration all
  reported v1.3.3 with publisher `Justichuu`;
- the installation ID, install directory, Swiss server selection, IKEv2 VPN
  profile, remembered-credential setting, and NordVPN root certificate were
  preserved;
- the installed directory contained exactly the 12 expected files, with no
  subdirectories or reparse points;
- application and state directories were owned by Administrators and used
  protected ACLs granting full control only to SYSTEM and Administrators and
  read/execute access to Users;
- all four Start menu shortcuts targeted the intended installed executables or
  scripts;
- no upgrade transaction directory, temporary state file, rollback file, or
  recovery journal remained.

The connection and kill switch were intentionally not armed during this audit
because doing so would change live network and firewall state. The incident is
closed: the published upgrade, deployed metadata, preserved configuration,
cleanup, and user-visible launch path are verified.
